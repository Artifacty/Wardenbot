# v0.2.0: обновление перед открытием

## Обновить существующий сервер

1. Остановите бота (Ctrl+C или systemd) и сделайте резервную копию SQLite по README.
   Не запускайте старую версию одновременно с новой.
2. Из корня репозитория на Windows выполните:

   ~~~powershell
   git pull
   cd wardenbot
   ..\.venv314\Scripts\python.exe -m pip install -r requirements-dev.txt
   ..\.venv314\Scripts\python.exe -m pytest -q
   ~~~

3. В существующем .env проверьте DB_PATH: это должна быть прежняя БД.
   Задайте BRIEFING_OPEN_MINUTES=45, если раньше выставляли 60.
   AUTO_CLOSE_HOURS больше не используется: завершение подтверждает организатор.
4. Для сохранения обсуждений включите Message Content Intent в Developer Portal → Bot
   и MESSAGE_CONTENT_INTENT=true в .env. Server Members Intent также должен быть включён.
5. Из той же папки запустите:

   ~~~powershell
   ..\.venv314\Scripts\python.exe -m wardenbot
   ~~~

   Миграция до схемы 7 автоматическая. Уже отправленные напоминания сохраняются.
   На Ubuntu обновите зависимости Python 3.14 venv и перезапустите systemd по HOSTING.md.
6. В Discord выполните /setup run, /setup status, /menu.
   При устаревших командах — /setup sync. Для одного сервера удобно оставить DEV_GUILD_ID
   равным ID этого сервера: команды регистрируются сразу в нём.
   Глобальные изменения Discord могут появиться с задержкой.

При откате остановите новый процесс и верните резервную БД вместе с совместимой версией кода.
Старая версия не должна работать с уже обновлённой схемой.

## Сценарий на тестовом сервере

Используйте организатора и отдельного обычного игрока. Администратор обходит проверки допуска.

1. Новичок открывает /menu → «Пройти проверку», указывает ник, получает код, отправляет
   один скриншот F1 и игрового чата через /verify screenshot. Модератор одобряет заявку.
2. Администратор открывает /menu → «Создать операцию». Представителям клана сначала нужны
   /clan register и /clan assign. Время вводится по /timezone set (по умолчанию Москва).
   Для быстрой проверки назначьте начало через 16 минут и одно место в роли «Пехота».
3. Игрок записывается. Второй игрок не должен занять заполненную роль. Повторное нажатие первым
   не создаёт вторую запись. Снятие записи закрывает дальнейший доступ к брифингу.
4. В «Управлении» измените название, время, требования, роли или ресурсы. Карточка обновится.
   Удаление занятой роли или ресурса с обещаниями запрещено. Чтобы переименовать занятую роль,
   сначала согласуйте переход участников. Устаревшая форма отклоняется.
5. Кнопка «Снабжение» сохраняет итоговое обещанное количество. Ноль отменяет недоставленное обещание.
   /operation supplies operation:ID показывает ID ресурсов и поставщиков.
   /operation delivery operation:ID resource:ID player:@Игрок amount:30 подтверждает итоговую доставку,
   а не прибавляет 30 при каждом вызове. «Начальные запасы» считаются отдельно от поставщиков.
6. Перезапустите бота до T−15. Основные кнопки и меню должны работать.
   Напоминание приходит один раз, без закрытого плана. Для проверки T−60 создайте операцию через 61 минуту.
7. Отметьте явку: /operation attendance operation:ID player:@Игрок attended:True.
   Начните операцию, затем «Завершить» → подтверждение. Простая запись не считается участием;
   подтверждённая доставка и явка одного человека дают один зачёт.
8. После итогового уведомления операция попадёт в архив, исходный пост удалится.
   При ошибке архива исходник не удаляется. Проверяйте журнал бота и /setup status.

Отдельно проверьте брифинг до T−45 и после, отзыв допуска со старой формой,
закрытие/открытие набора после начала, перенос времени и отмену с публичной причиной.
Подробный план пишите только в закрытом брифинге.

## Модерация

- /moderation revoke player reason — отзыв допуска, снятие активных записей, новая проверка.
- /moderation newwar number — после подтверждения запускает повторную проверку;
  администрация исключена, история сохраняется. Проверяйте на тестовом сервере:
  команда меняет допуск всего сообщества.
- /moderation timeout player minutes reason — мут до 28 дней; minutes:0 снимает его.
- /moderation ban player reason и /moderation unban user_id reason — бан/разбан без удаления сообщений.

Проверяются полномочия и иерархия. Роль бота должна быть выше управляемых ролей.

## Проверки и ограничения

Тесты используют настоящий SQLite, миграции и конкурентные вызовы; ответы Discord моделируются.
Проверяются меню, лимиты мест, конфликт форм, доступ T−45, отзыв допуска, поставки, участие,
уведомления после потери подтверждения, архив до удаления и блокировка второго процесса.
Живой сценарий выше обязателен перед открытием.

- Один экземпляр на одну БД и один Discord-сервер. Полной изоляции профилей между серверами пока нет.
- Данные, очереди и основные кнопки переживают перезапуск. Незаконченные черновики и открытые
  формы нужно открыть заново. Повторная публикация одного черновика не создаёт вторую операцию.
- При неопределённом результате публикации сохраняется строка БД; бот ищет пост по его ID.
  /operation recover operation:ID запускает сверку. Если пост не найден, отмените запись через
  /operation manage перед созданием другой. Бот не повторяет публикацию вслепую.
- Не удаляйте сообщения бота при обработке очереди: если потеряны и подтверждение, и сообщение,
  невозможно достоверно установить доставку. В остальных случаях служебная метка позволяет сверку.
- Архив фиксирует снимок. Поздние исправления явки учитываются в БД и ролях, но не переписывают файл.
  Текст обсуждения сохраняется; вложения сохраняются ссылками, которые могут истечь.
- Сеть и права Discord могут задержать выдачу роли, уведомление или архив. Задание остаётся для повтора.
  Отозванный в БД допуск уже блокирует действия бота; снятие Discord-ролей зависит от успешного API-запроса.
- Уже прочитанный приватный ответ отозвать нельзя; после снятия записи новые запросы отклоняются.
- EN, перевод, сайт и расширение магазина в этот выпуск не входят.
